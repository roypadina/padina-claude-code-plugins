# Taxonomy guide — how to judge a vault's structure

Derive the areas per vault; never copy another vault's list.

## One axis at the top

Top-level folders must all answer the same question — "which area of life or work is this?" — not a mix of *by tool* (`Notion/`, `Readwise/`), *by kind* (`Articles/`), *by subject* (`Garden/`) and *by area* (`Home/`). Mixed axes are the usual rot: an agent cannot tell where a new note goes, so it asks or guesses.

Palette of areas (pick 3–6, name them in the vault's own words):

| Area | Holds | Typical owner |
|---|---|---|
| Personal | life admin, home, family, finance, recipes, health, travel | human |
| Work | employer / client content — may be "none here by policy, lives in vault X" (write that rule down) | human |
| Technical / Engineering | standards, reference knowledge bases, tool and product research | human + research skills |
| Infra | home lab, servers, network, home automation, self-hosted services, alerting rules | human + ops skills |
| Setup | device and software notes, config exports — often generated by tools | machine |
| Projects | undertakings with a start and an end; archive when done | human |
| Archive | finished material kept for reference; never restructured | — |

Second level = subject inside the area (`Infra/Network/`, `Personal/Travel/`). Third level only for ordered series or machine trees.

## Signals that need a change

- Single-note folders (fold into a sibling, or into the parent as a note).
- Typos and abbreviations in folder names — fix them; every agent reads these names.
- A folder named after a tool when its purpose is the real subject (`Docker/` → part of Infra; `VS Code/` → Setup).
- Two folders with the same meaning (`Tools/` and `Apps/`; `Research/` and `Reading Notes/`).
- Loose notes at the root, draft/scratch notes, dated notes without a log folder.
- >300 notes in one folder without sub-structure, unless machine-written (then collapse it in the index, never hand-sort it).
- Machine-written mirrors (config backups, generated catalogs) mixed with hand-written notes in the same folder level.
- Hub/index notes written by hand that duplicate the generated index — keep them if they add prose, otherwise drop.

## Cost of a move

Outside refs are the expensive part — each one is a file to edit and possibly a program to re-test; settings files that exist in several copies (one per config dir) count once per copy; installed caches cannot be edited and need a reinstall. In-vault path-style links and the registry are cheap (script-fixed). Basename wikilinks survive folder moves untouched; a *rename* of a note changes them (the script follows unique basenames only).

Rule of thumb: the cheap set (typos, loose notes, single-note folders) is always worth it. Structural top-level moves are worth it only when the axis is broken or an area is missing; then do them all in one review so references are rewritten once.

## Naming

- Folders: Title Case with spaces, the vault's language per area; no abbreviations.
- Notes: one convention per vault, derived from the existing names and written into the Structure note § Naming (`<Subject> — <qualifier>`, series codes `XY-01 <Part>`, numbered `1. `, hubs `00 <Name>` are all fine); exceptions listed with the folder that pins them (a plugin, a generator).
- Machine-written trees keep the writer's naming; document it in the Folder map instead of fighting it.
